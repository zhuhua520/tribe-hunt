## 1. 文档优先级与使用方式

Cursor 开始新任务前，按以下顺序理解项目：

1. 用户最新明确确认的方向，优先级最高。
2. 《docs/后续开发指导方案-暂时可玩版本.md》决定当前开发顺序、阶段边界和每阶段的退出条件；本文保留早期里程碑细节与历史验收记录。
3. 《部落远征-完整设计方案-v2.md》提供玩法与功能设计基准；新指导方案明确调整的开发顺序优先于 v2 中较早的里程碑排序。
4. 《docs/Godot开发规范与约定.md》和《.cursor/rules/godot-project.mdc》约束实现方式。
5. 《docs/进度.md》和《docs/交接文档.md》记录实际完成状态。记录必须以实际代码和已执行验证为准。

本文中的阶段是建议的施工顺序。遇到尚未讨论确定的玩法规则，Cursor 应保留接口或暂不实现，不得因为进入某个技术阶段而顺手定案。

## 2. 当前项目基线

### 已完成

- **M0 单人战斗原型**：玩家移动、木棍近战与弹弓远程自动攻击、固定三波敌人、胜负流程。
- **M1 基础流程**：主菜单、单人出征准备、设置、暂停与结果页、创意工坊占位。
- **设置存档**：主音量和窗口模式保存在本地设置文件中，并已记录相应验证。
- **2.1.1 本机会话**：ENet 创建/加入/离开；人工双开 UI 复验已通过。
- **2.1.2 玩家身份与移动同步**：移动测试场景中按 peer 身份生成角色；客户端提交移动意图，服务器权威位置同步；断开清理角色。
- **2.1.3 敌人与波次状态同步**：服务器生成并驱动敌人，客户端只显示权威位置与波次状态。
- **2.1.4 攻击、伤害与胜负权威**：联机测试场由服务器结算临时自动攻击、敌人生命、接触伤害和胜负。单人战斗未改。

### 已确认方向（2026-10-16）

- 玩家核心操作是移动和攻击，不加入主动技能。自动攻击和手动攻击都做单人小原型后再比较；自动攻击可以设为开关。「是否做自动/手动对照」已确认，不再作为未决事项。对照结束后保留哪一种操作，仍看原型结果。
- 撤离点开放节奏留待原型比较。合作时队伍一起行动，并通过投票决定撤离或继续。投票时长、平票、离线成员和奖励归属仍未定。
- 阶段 3.2 的两个模块、+20% 数值和直接选择方式继续作为临时测试基线，不是最终构筑规则。

### 尚未实现或尚未验证

- **2.2 局域网冻结，待真实双设备联调。** 2026-10-16 只在本机确认房主监听 `0.0.0.0:7777`，并回归了单人竞技场。没有第二台设备完成对局，不能写成已通过。用户已明确要求先冻结 2.2、继续阶段 3；以后有设备时再恢复人工联调。云服务器跨网尚未开始。
- 好友邀请、公开房间搜索和 Steam 尚未接入；创意工坊入口仅占位。
- 玩家成长、模块/武器收藏和联机奖励存档尚未实现；其数据归属要等玩法规则确定后处理。
- 单人自动/手动攻击对照的代码尚未开始。2026-10-16 用户未采用「一个攻击键出手、自动选择最近有效目标」；手动目标选择继续讨论。确认前不实现出手或瞄准方向。
- 奖励规则、成长存档、掉落和星座效果仍未定，当前不实现。

### 工作区保护

工作区可能仍有未提交的 M1/联机相关修改。Cursor 每次开始前必须检查 Git 状态并保留当前工作；禁止用重置、清理或覆盖方式“整理”工作区，也不要擅自提交或暂存无关改动。

## 3. 早期目标与联机方向记录（当前单人排期以后续指导方案为准）

早期路线为本机双开 → 局域网 → 基础玩法原型。用户决定先完成暂时可玩的单人远征闭环和首轮视觉工作，再恢复合作/联网验证。下列联机里程碑仍用于记录已完成与后置边界，当前单人开发任务顺序见《docs/后续开发指导方案-暂时可玩版本.md》：

1. 已完成同一台电脑运行两个游戏实例的本机联机闭环（2.1.1–2.1.4）。
2. 2.2 局域网测试仍待真实设备验证，目前按用户要求冻结，不阻塞阶段 3。
3. 当前实现阶段 3 最小构筑原型；完成基础玩法原型后，再根据玩法状态和联机需要讨论云服务器接入。

已确认的范围边界：

- 云服务器仍是未来跨网络测试及权威运算的目标，但不紧接局域网测试实施；等基础玩法有可玩实现后再评估和排期。
- 从第一版多人战斗开始，服务器负责校验关键操作并计算敌人行为、伤害、波次和最终结果。未来加入掉落、道具与奖励时，也由服务器计算和确认。
- 客户端提交输入或动作意图，不直接提交伤害数字、掉落内容或结算结果。
- 本机和局域网阶段可以由房主游戏进程兼任服务器。当前继续按服务器权威方式实现战斗逻辑，为未来迁移保留边界；暂不做 headless 导出、云端部署或跨网联调。
- 未来云端原型预计从一个手动连接的测试房间开始；公开房间搜索、自动匹配、Steam 好友邀请和多房间调度仍属更后续范围。
- Steam 邀请、公开房间搜索继续作为后续入口/占位；创意工坊继续占位。
- “本机双开”是两个独立游戏进程进行网络测试，不等同于同屏本地合作。本地合作的玩家数、镜头和输入方案仍待原型比较。
- 已确认合作队伍一起行动，撤离点由投票决定。撤离点按每波还是每若干波开放，留待原型比较。奖励归属、投票时长、平票和离线成员处理仍未定，不在当前单人攻击对照中实现。

初始传输原型建议使用 Godot 内置高层多人 API 与 ENet/UDP，创建房间、加入地址、离开会话先做最小实现。该选择服务于当前原型，不代表已决定未来 Steam 传输或发行架构。若现有工程条件使其不可行，Cursor 应先说明阻碍和替代方案，不要静默换技术栈。

## 4. 阶段路线

### 阶段 1：战斗与基础流程（已完成）

- M0：单人三波战斗原型。
- M1：主菜单、单人入口、设置存档、暂停/结果流程与工坊占位。

除修复当前阶段暴露的问题外，不重复实现 M0/M1。

### 阶段 2：最小联机基础（2.1 已完成；2.2 冻结待恢复）

#### 2.1 本机双开

按以下小任务逐个完成。每个任务完成、验证并更新进度/交接后，停止等待下一条明确任务，不自动继续后续任务。

**2.1.1 创建、加入与离开会话**

- 主菜单的在线入口提供最小化的“创建测试房间”和“输入地址/端口加入”流程。
- 房主本地创建监听会话；另一进程通过本机地址连接。
- 显示连接中、连接成功、连接失败和离开会话的状态；失败或重复点击不应使游戏崩溃。
- 不接 Steam，不做公开房间列表，不实现房间浏览器。

验收：两个独立游戏实例可以创建/加入/离开；错误地址能得到可理解的失败反馈；离开后可回到菜单并重新创建或加入。

**2.1.2 玩家身份、生成与移动同步**

- 为每个连接玩家建立稳定的会话内身份映射。
- 每个客户端只控制自己的角色；其他玩家角色可见并能正确同步移动。
- 网络消息传递输入/动作意图，由服务器维护并广播权威位置；首轮不做预测或回滚。
- 单人流程继续可玩，不让多人初始化影响单人模式。

验收：两个实例都能看到两个不同玩家；双方各自移动时不会控制同一个角色或互相覆盖输入；退出一名玩家后其角色被清理。

**2.1.3 敌人与波次状态同步**

- 服务器负责敌人生成、移动/行为和波次推进。
- 客户端显示服务器确认的敌人和波次状态。
- 不加入掉落、背包、撤离投票或跨局奖励。

验收：两个实例看到一致的敌人数量和波次推进；由服务器结束的战斗状态在两端一致。

**2.1.4 攻击、伤害与胜负权威**

- 客户端发送攻击输入/意图；服务器验证并结算命中、敌人生命值、玩家受伤和胜负。
- 不能由客户端直接声明伤害值、敌人死亡或整局胜利。
- 处理玩家离开会话后的节点清理；暂不实现重连、房主转移和掉线恢复。

验收：双开重复完成一局时，双方看到一致的敌人死亡、玩家状态、波次和胜负结果；单人战斗仍能运行。

**2.1 本机阶段总退出条件**

- 两个本机进程可多次完成“创建/加入—战斗—结果—离开—重新开始”。
- 一致性以服务器状态为准；没有客户端本地伪造伤害/奖励结果的路径。
- 关键断开路径有反馈，场景切换后没有遗留玩家或会话状态。
- 已执行的验证逐项写入进度文档；未能在 Cursor 所在机器验证的项目标为“待人工验证”，不能标成完成。

#### 2.2 局域网测试

**状态：冻结，等待后续真实双设备联调。** 本机已确认 Godot 4.7.2 房主监听全部 IPv4 接口的 UDP 7777，且主菜单到单人竞技场仍可打完一局。当前环境没有第二台设备，未改防火墙，本机双开不等于 2.2 通过。用户已决定先继续阶段 3；人工步骤保留在 `docs/交接文档.md`，有设备时再恢复。

- 使用同一版本，在两台真实设备上测试；客户端手动输入房主的局域网地址和端口。
- 验证连接、玩家生成/移动、敌人/波次、攻击/伤害、胜负、离开与重新开局。
- 记录 Godot 版本、设备、网络环境、端口和失败现象；操作系统防火墙提示需明确说明。
- 不在本阶段加入公网穿透、Steam 中继、房间搜索或账号系统。

退出条件：两台设备在同一局域网能稳定完成一局并退出，单人回归路径正常。若 Cursor 无法访问第二台设备，应交付清晰的人工测试步骤并把此项标为待验证。

#### 2.3 存档边界

- M1 的本地设置存档已经完成，不重复造轮子。
- 当前阶段不实现武器/模块收藏、远征收益、联机奖励或云存档；这些数据的稳定 ID、所有权和结算规则尚未确定。
- 若联机调试确实需要保存测试设置，只复用现有设置存档，不把临时战斗状态混入设置文件。
- 玩家进度存档在构筑数据与奖励归属规则确认后另设小阶段。

### 阶段 3：武器、模块与星座的最小构筑原型

用户已明确要求在 2.2 冻结期间继续本阶段；2.2 仍记为未验证。目标是验证“带什么、如何组合、战斗中如何调整”，不是填充大量内容。完成可玩的构筑/战斗基础后，再讨论云服务器是否进入实施。

- 少量武器和少量模块，足以产生可观察的构筑区别。
- 武器字段保留品质、稀有度、属性加成、固有属性、武器专属特效和强化上限；只做两个容易区分的稀有度用于验证，其余细节按当前设计保留占位。
- 模块字段保留类别、初始星级/强化等级、元素值、武器适配标签和特殊属性词条；元素效果首轮不参与玩法，统一按无属性处理。
- 星座分别记录独特星点的收集完成度、当前装备的套装件数和完整收集奖励位置；具体效果先占位。
- 普通适配优先使用容易理解的武器类别标签；专属适配只留给少量特殊模块或神器，不让一般模块绑定唯一武器。
- 不加主动技能栏，不通过大量被动词条制造组合量，不提前确定最终数值、资源消耗或永久掉落规则。

#### 3.1 构筑数据层与最小预览（已完成，2026-10-16）

- 用 Godot `Resource` 表达静态武器、模块、星座定义；运行中的装备与收集状态放在独立运行时数据中，不修改共享定义资源。
- 使用现有木棍与弹弓作为少量武器样例；保留两档易区分的稀有度标识。品质/稀有度其他行为、掉落概率、武器特效和强化上限只保留字段，不据此扩写玩法。
- 模块只承载当前确认的类别、初始星级/强化等级、属性加成字段、元素值、武器适配标签、特殊属性词条占位；元素按无属性处理，不应用模块效果。
- 星座以稳定星点 ID 分开记录“已发现的独特星点”和“当前装备的该星座模块件数”；完整收集奖励及套装奖励效果保留空定义，不确定具体门槛/效果。
- 做一个独立、临时的构筑预览场景供开发验证数据和两种计数；不增加正式主菜单入口，不保存玩家成长数据，不接入联机测试场景，也不确定武器/模块槽位上限。
- 预览中的收集与装备测试控件只用于分别验证计数，不代表掉落、解锁前置、重复模块能否同时装备等规则已经确定。
- 验收：预览能显示样例定义；收集同一星点不会重复增加完成度；装备/卸下模块只影响装备件数；两类计数始终分别可见。执行项目规定的 Godot 运行验证和单人入口回归，并如实记录结果。

#### 3.2 武器/模块效果与局内调整（单人最小原型已完成，2026-10-16）

- 在单人出征准备页直接勾选当前两个模块样例，作为本次运行的测试构筑；不做收藏、解锁、掉落、背包或槽位上限。
- 近战样例模块临时提供近战攻击速度 +20%；远程样例模块临时提供远程攻击范围 +20%。这些数值只用于验证差异，不是最终平衡或长期规则。
- 每个非最终波次清场后暂停整局，允许玩家增减样例模块；确认后恢复波间等待并进入下一波。HUD 显示当前生效构筑。
- 通过独立运行时服务计算效果；静态 Resource 定义不在战斗过程中被改写。出征选项与局内调整只影响本次单人运行，不进入存档。
- 当前只接入单人竞技场。没有改多人测试场、SessionService、服务器权威结算或任何网络同步；2.2 仍冻结。
- 验收：从主菜单进入单人出征准备，选择样例模块并进入战斗；非最终波结束时可调整并继续；HUD 随调整更新；三波胜负流程可正常结束。执行脚本验证和完整单人运行回归。

本原型没有确定最终模块效果、数值、取得方式、槽位和成长规则。测试界面直接提供两个样例供选择，只为快速验证构筑选择和局内调整。需要用户体验后再决定是否改规则或扩展星座效果。

退出条件：构筑示例能表现至少两种不同战斗倾向；玩家能读懂主要适配关系；局内调整带来真实选择；独特星点收集与装备件数没有混成一个计数。验证后再讨论扩充内容和长期存档。

### 下一开放任务：单人自动/手动攻击对照（方向已确认，实现未开始）

### 当前联机同步模型审查（代码现状）

- 联机实现是服务器权威的输入/状态同步，**没有帧同步或确定性锁步**。当前阶段 3.2 是单人构筑原型，没有改网络代码或增加同步内容；帧同步评估仍等 2.2 多设备联调恢复后另行安排。
- 客户端每个物理帧用 reliable RPC 提交移动向量；服务器每个物理帧向客户端发送玩家/敌人位置，位置用 `unreliable`，接收端直接设置坐标；投射物位置也逐物理帧发送。波次、生命、生成/移除等离散结果用 reliable RPC。
- 未见显式帧号/快照序号、客户端预测、远端插值或回滚。客户端移动需经服务器往返，跨网可能感到输入延迟；因 `unreliable` 允许丢包和乱序，且客户端直接应用位置，局域网/跨网可能出现抖动或旧位置覆盖；逐帧 reliable 输入遇到网络拥塞也可能积压。当前本机双开验证不能证明多设备表现。
- 当前不改网络代码或加帧同步。恢复 2.2 后先在真实设备观察，再把状态采样、序号/传输模式、插值/预测作为独立联机改进任务评估。Godot 参考：[高层多人游戏 API](https://docs.godotengine.org/en/4.7/tutorials/networking/high_level_multiplayer.html)。
