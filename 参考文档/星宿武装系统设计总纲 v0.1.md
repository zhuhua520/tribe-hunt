# 星宿武装系统设计总纲 v0.1

**文档类型：** 核心游戏设计文档  
**版本：** v0.1  
**状态：** 初步设计基准，部分细节待确认

## 1. 项目目标

以中国古代三垣、二十八宿和星官体系为文化基础，构建一套融合战斗 Build、Boss 挑战、组件收集、基地建设、外观收藏与探索的游戏内容体系。

玩家从初始星盘和基础组件出发，通过探索区域、击败 Boss、完成挑战等方式逐渐收集组件，组合出不同的战斗 Build，并解锁非战斗类奖励。

系统必须同时满足：

1. 核心规则简单，玩家容易理解。
2. 不同组件组合能够形成有辨识度的战斗玩法。
3. 历史资料与原创游戏机制严格区分。
4. 不强制将每个星宿、星官都制作成战斗装备或 Boss。
5. 控制随机掉落、库存管理和长期成长的复杂度。
6. 方便持续增加星宿、星官、武器、区域和奖励内容。

## 2. 设计原则

### 2.1 历史资料优先

三垣、二十八宿、星官的名称和传统关系，以后续选定的历史文献及星表为依据。

不得为了套装效果、Boss 设计或奖励分配而擅自改变历史归属。

历史资料与游戏玩法分别记录。游戏可以选择性使用历史内容，但不能将原创游戏效果描述成古代天文学事实。

### 2.2 游戏内容允许删减

历史目录可以保持完整，但进入实际玩法的内容可以经过筛选。

不适合战斗设计的内容，可以转化为：

- 时装、武器外观、角色特效。
- 基地设施、设施升级与装饰。
- 探索、解谜和隐藏奖励。
- 图鉴、背景故事和收藏成就。

不要求每个星宿都必须有独立战斗 Boss，也不要求每个星官都必须成为可装备组件。

### 2.3 核心规则优先

战斗 Build 的基础结构采用：

**一宿两官：一个星宿核心、两个星官组件。**

不在第一版中引入多层套装、复杂容量计算或强制的五行相生相克系统。

### 2.4 自由组合优先

星宿提供核心战斗机制，星官提供相对独立的特殊效果。

星官可以跨宿搭配。传统所属关系可以用于内容分类、奖励安排和可选的专属联动，但不应限制所有组件只能与本宿组合。

### 2.5 随机性与可理解性并重

同名组件具有固定身份和固有核心效果，掉落时随机生成副词条。

随机性用于产生不同的组件实例，不应改变组件的基本玩法身份。

## 3. 历史资料层与游戏玩法层

系统分为三个逻辑层。

### 3.1 历史资料层

负责记录：

- 标准名称与别名。
- 历史分类及传统所属关系。
- 相关恒星、星数和星区信息。
- 参考文献、版本与核验状态。

具体历史关系必须在选定资料版本后核验。

### 3.2 游戏内容层

负责记录：

- 是否进入战斗 Build。
- 是否关联区域或 Boss。
- 是否提供基地、外观或探索奖励。
- 游戏中的关联星宿、关联星官。
- 奖励来源和解锁条件。

游戏关联不得覆盖历史归属。

### 3.3 战斗机制层

负责记录：

- 固有核心效果。
- 随机副词条池。
- 元素属性与数值。
- 适用的攻击行为标签。
- 强化规则及数值限制。

具体战斗效果均属于游戏原创设计。

## 4. 星盘与 Build

### 4.1 星盘归属

星盘属于角色，不绑定某一件具体武器。

玩家更换同类武器的不同品级时，已配置的 Build 原则上继续生效。

### 4.2 固定装配结构

每套战斗 Build 包含：

- 1 个星宿核心。
- 2 个不同的星官。

每套 Build 必须装备一个星宿核心，不能仅由星官组成。

### 4.3 组件复用

同一件组件实例可以被多套已保存的 Build 引用，不需要为了切换武器或流派重复收集。

同一套 Build 内不允许重复装配同名星官。

正在被 Build 引用的组件不得直接拆解；应先解除引用或提示玩家处理。

### 4.4 专属联动

同一核心星宿与相关星官之间可以存在专属联动，但该联动属于游戏规则。

专属联动不应成为组件基础效果生效的必要条件。其具体触发条件和数值尚未最终确定。

## 5. 武器与 Build 的职责划分

### 武器负责

- 基础攻击方式。
- 攻击动作与战斗节奏。
- 武器自身的攻击特效和特殊机制。
- 武器基础属性、品级与自身词条。

### Build 负责

- 核心战斗机制。
- 属性加成。
- 条件触发效果。
- 破甲、暴击、失衡、元素积累等战斗机制的强化。
- 组件之间的可选联动。

### 战斗系统负责

- 攻击命中与伤害结算。
- 暴击、破甲和元素积累判定。
- 组件触发条件的判断。
- 对应的视觉和音效反馈。

原则：新增组件时尽量复用已有战斗机制，不为每个组件创建全新的资源系统或独立战斗系统。

## 6. 组件属性规范

每个战斗组件至少记录：

| 字段 | 说明 |
|---|---|
| 名称 | 星宿或星官的标准游戏名称 |
| 类别 | 星宿 / 星官 |
| 初始星级 | 固定的 1—5 星品质 |
| 强化等级 | 玩家培养进度，具体上限待定 |
| 元素类型 | 木、火、土、金、水之一或后续明确规定的组合 |
| 元素值 | 对应的基础元素贡献 |
| 攻击行为标签 | 例如蓄力、重击、多段命中、投射物 |
| 固有核心效果 | 固定的基础机制 |
| 随机词条池 | 允许抽取的副词条集合 |
| 历史归属 | 经核验的传统关系 |
| 游戏关联 | 用于游戏玩法的关联关系 |

并非所有历史星宿、星官都必须填写战斗组件字段。非战斗内容使用对应的奖励与玩法数据。

## 7. 星级与成长原则

同名组件的初始星级永久固定。

高星组件通过更高难度的内容获取，不通过升星改变品质。

星级决定初始数值档位与成长潜力，但不能单独决定组件的构筑价值。

已经确认的平衡方向：

- 五星组件的数值优势适中。
- 低星组件可以长期有效。
- 构筑适配度和机制价值比单纯星级排名更重要。
- 星级不改变固有核心机制。
- 星级不增加随机副词条数量。

具体数值成长曲线、强化上限、强化成本与星尘经济暂缓设计。

## 8. 获取与奖励

核心循环：

探索区域 → 挑战 Boss 或完成活动 → 获得组件及其他奖励 → 组合 Build → 挑战更高难度内容。

奖励可以包括：

- 星宿核心组件。
- 星官组件。
- 强化资源。
- 时装与武器外观。
- 基地设施蓝图和升级材料。
- 图鉴、剧情与隐藏探索奖励。

重要 Boss 的核心奖励可优先采用确定性获取，以保证玩家能够逐步构筑。

重复挑战的具体奖励、概率和保底机制尚未确定。

## 9. 非战斗内容

非战斗奖励与战斗组件共同属于星宿收集体系，但不强制进入 Build。

同一星宿或星官可以关联多个奖励类别，例如战斗挑战、隐藏探索和外观收藏。

三垣的具体游戏职责暂不锁定。可考虑将其用于高层级区域、挑战路线或图鉴组织，但需要后续讨论。

## 10. 组件库存管理

基础规则：

- 组件可以保留、收藏、锁定或拆解。
- 支持按类别、星级、强化等级和词条筛选。
- 支持比较同名组件的随机词条。
- 锁定组件不能被批量拆解。
- 图鉴记录独立于实际组件实例，拆解不影响收集记录。
- 拆解不需要的组件可获得通用成长资源，暂定名称为“星尘”。

词条重铸、定向制作和其他复杂制作系统暂不加入第一版。

## 11. 第一阶段验收目标

第一阶段不要求完整制作全部二十八宿。

优先验证：

1. 玩家能否快速理解“一宿两官”。
2. 更换星宿是否能够改变核心战斗方向。
3. 更换星官是否能改变同一星宿的构筑路线。
4. 同名组件的随机词条是否产生有意义的差异。
5. 低星组件是否仍有适用场景。
6. 组件收集、拆解与 Build 复用是否形成清晰闭环。

## 12. 待讨论事项

- 战斗系统的具体类型与攻击行为定义。
- 初始星盘和初始组件配置。
- 历史资料采用的正式参考版本。
- 各星宿与星官的实际内容分配。
- 星级分布和具体数值。
- Boss 区域与奖励进度。
- 专属联动的最终规则。
- 强化成本、星尘经济及后期成长曲线。
