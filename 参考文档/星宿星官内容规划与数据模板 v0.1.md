# 星宿星官内容规划与数据模板 v0.1

**用途：** 统一历史资料采集、游戏内容规划、组件定义与掉落实例数据。

## 1. 内容制作原则

历史资料与游戏设计分别维护。

历史资料用于记录可核验的名称、归属、恒星和文献来源。

游戏设计用于决定是否进入战斗 Build、区域挑战、基地设施、外观收藏或探索内容。

不得为了平衡组件数量而更改传统星官归属。

## 2. 历史资料表

每个星宿或星官建立一条历史资料记录。

| 字段 | 说明 |
|---|---|
| history_id | 历史条目唯一标识 |
| standard_name | 标准名称 |
| aliases | 别名 |
| historical_type | 三垣、二十八宿、星官或其他经核验的类别 |
| historical_parent | 参考文献中的传统目录位置 |
| related_region | 经核验的相关天区 |
| star_count | 可靠资料支持时记录星数 |
| star_references | 相关恒星资料 |
| source_title | 参考文献名称 |
| source_version | 文献或星表版本 |
| verification_status | 待查、已核验、有争议 |
| notes | 版本差异及说明 |

历史归属在完成资料核验前，不得作为最终游戏关联的唯一依据。

## 3. 游戏内容规划表

每条历史记录可以关联一个或多个游戏内容项目。

| 字段 | 说明 |
|---|---|
| content_id | 游戏内容唯一标识 |
| history_id | 对应历史资料 |
| gameplay_type | 战斗、基地、外观、探索、图鉴 |
| implementation_status | 未规划、规划中、制作中、已完成 |
| region_id | 对应游戏区域 |
| boss_id | 对应 Boss；没有则留空 |
| reward_ids | 相关奖励 |
| game_associations | 游戏内关联星宿或星官 |
| rationale | 设计理由 |
| historical_distinction | 是否包含原创游戏设定的说明 |

同一个星宿或星官可以拥有多条游戏内容记录。例如，核心挑战可以提供战斗组件，隐藏探索可以提供外观奖励。

## 4. 组件定义表

仅对进入战斗 Build 的内容建立组件定义。

| 字段 | 说明 |
|---|---|
| component_id | 组件定义唯一标识 |
| history_id | 对应历史条目 |
| name | 游戏显示名称 |
| category | 星宿 / 星官 |
| fixed_star_rating | 固定初始星级 |
| base_element_type | 基础元素类型 |
| base_element_value | 基础元素值 |
| base_stats | 基础属性 |
| core_effect_id | 固有核心效果 |
| attack_tags | 适用攻击行为标签 |
| affix_pool_theme | 主题词条池 |
| affix_pool_general | 通用词条池 |
| max_affix_count | 当前设计基准为 2 |
| gameplay_associations | 游戏内关联关系 |
| acquisition_source | 获取来源 |
| notes | 设计备注 |

固定星级和固有核心效果属于组件定义，不能在每次掉落时随机改变。

## 5. 组件实例表

玩家每次获得组件时生成独立实例。

| 字段 | 说明 |
|---|---|
| instance_id | 组件实例唯一标识 |
| component_id | 对应组件定义 |
| initial_star_rating | 从组件定义继承 |
| enhancement_level | 当前强化等级 |
| rolled_affixes | 本次生成的两条随机副词条 |
| locked | 是否锁定 |
| favorited | 是否收藏 |
| dismantled | 是否已拆解 |
| acquisition_source | 获取来源 |
| acquired_at | 获取记录 |

同名组件可以拥有多个实例，每个实例具有独立的随机词条和强化状态。

## 6. 随机词条定义表

| 字段 | 说明 |
|---|---|
| affix_id | 词条唯一标识 |
| name | 显示名称 |
| category | 攻击、机制、元素、生存 |
| eligible_components | 允许出现的组件范围 |
| eligible_tags | 适用的攻击行为标签 |
| value_min | 数值下限 |
| value_max | 数值上限 |
| stacking_rule | 同类效果叠加规则 |
| rarity_weight | 抽取权重；具体数值待定 |
| description | 玩家可读说明 |
| implementation_status | 设计、实现、测试状态 |

词条数值、权重和叠加规则需要由设计数据明确配置，不得依靠程序任意生成。

## 7. Build 配置表

| 字段 | 说明 |
|---|---|
| build_id | Build 唯一标识 |
| name | 玩家自定义名称 |
| core_instance_id | 星宿核心实例 |
| star_officer_a | 第一件星官实例 |
| star_officer_b | 第二件星官实例 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

校验规则：

- 必须存在一个星宿核心。
- 必须存在两个星官。
- 两个星官不能同名。
- 三个位置均引用有效组件实例。
- 同一实例可以被不同 Build 复用。
- 被多个 Build 引用的组件不得重复计算属性。

## 8. 奖励与掉落规划表

| 字段 | 说明 |
|---|---|
| reward_id | 奖励唯一标识 |
| source_type | Boss、探索、任务、设施或其他来源 |
| source_id | 来源唯一标识 |
| reward_type | 组件、资源、外观、蓝图、图鉴 |
| component_id | 对应组件定义；不适用时留空 |
| guaranteed | 是否确定性奖励 |
| drop_weight | 掉落权重；具体值待定 |
| unlock_condition | 解锁条件 |
| repeat_reward | 重复挑战的奖励规则 |
| notes | 设计备注 |

重要 Boss 可以保证获得指定核心组件。具体掉落概率、重复奖励与保底规则暂不确定。

## 9. 示例组件定义

以下仅展示数据组织方式。名称、属性和效果中的示例数值与原创战斗机制，不能当作历史事实或最终平衡值。

```json
{
  "component_id": "example_jiaosu",
  "name": "角宿",
  "category": "star_mansion",
  "fixed_star_rating": null,
  "base_element_type": null,
  "base_element_value": null,
  "core_effect": {
    "name": "示例：蓄力破甲",
    "description": "蓄力攻击命中时，额外积累破甲值",
    "status": "original_game_design_example"
  },
  "attack_tags": [
    "charge_attack"
  ],
  "affix_pool_theme": [
    "charge_damage",
    "armor_break"
  ],
  "affix_pool_general": [
    "critical_chance",
    "element_accumulation"
  ],
  "max_affix_count": 2,
  "historical_verification_status": "pending"
}
```

正式录入时，必须填入经过确认的星级、元素属性、词条池和历史资料引用。示例中的空值不是正式设计值。

## 10. 推荐的制作顺序

1. 选定历史文献与星表版本。
2. 建立完整的历史资料目录。
3. 对名称、归属和版本差异进行核验。
4. 筛选适合战斗和非战斗玩法的内容。
5. 建立第一批组件定义。
6. 设计少量星宿、星官与区域奖励，验证核心循环。
7. 根据实际测试调整星级分布、词条池和数值。
8. 再逐步扩展到更多星宿与星官。

## 11. 暂缓事项

- 最终星级比例。
- 每个星宿、星官的具体游戏用途。
- 最终元素值与属性预算。
- 具体词条数值和掉落概率。
- 强化上限、强化成本和星尘经济。
- 三垣的完整区域与进度设计。
- 全部二十八宿的 Boss 与奖励配置。
